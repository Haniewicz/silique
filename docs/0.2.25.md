# Silique 0.2.25+34 — draft, nie publikować bez osobnej zgody

Zakres: Windows, ponowny start z `SQLITE_IOERR_WRITE` (778) na
`%USERPROFILE%\Documents\Silique Vaults`. **Przyczynę na komputerze właściciela
potwierdzono** — inaczej niż w 0.2.21–0.2.24, gdzie pozostawała hipotezą.

## Potwierdzona przyczyna

Folder z notatkami jest chroniony przez Windows **Kontrolowany dostęp do
folderów** (Defender, „Ochrona przed oprogramowaniem wymuszającym okup”).
Zdarzenia sieciowe Defender `1123` wskazują dokładnie `silique.exe`:

| Zdarzenie 1123 (lokalnie) | Wpis diagnostyczny aplikacji |
|---|---|
| 21:48:23 | 21:48:19 `storage_open_failure … 778` |
| 22:05:52 | 22:05:49 `storage_open_failure … 778` |
| 22:06:27 | 22:06:23 `storage_open_failure … 778` (GetLastError=5) |

Treść zdarzenia: „Funkcja Kontrolowany dostęp do folderu zablokowała aplikacji
`C:\Users\Ultro\AppData\Local\Programs\Silique\silique.exe` możliwość
zmodyfikowania folderu `%userprofile%\Documents\Silique Vaults`.”

Niezależne odtworzenie poza aplikacją (Python 3.14, sqlite 3.53.1, ten sam plik):

- utworzenie dowolnego nowego pliku w `%USERPROFILE%\Documents` i w `Silique
  Vaults` kończy się błędem systemowym 2, podczas gdy w `%USERPROFILE%` i na
  pulpicie udaje się — to nie jest problem ścieżki ani uprawnień ACL (właściciel
  ma `FullControl`);
- `sqlite3.connect(..., mode=ro)` **też** kończy się `disk I/O error`: SQLite
  potrzebuje zapisu pliku `-shm`, żeby odczytać WAL, więc zablokowany folder jest
  nieczytelny dla SQLite, mimo że pliki są czytelne dla systemu;
- bajtowa kopia `silique.sqlite` + `-wal` do folderu spoza ochrony otwiera się
  poprawnie: `quick_check=ok`, 12 dokumentów, 2672 rewizje, 2 vaulty.

Wniosek: poprawka 0.2.24 (`locking_mode=EXCLUSIVE` przed odczytem schematu,
indeks WAL w pamięci) nie mogła tu pomóc — blokowany był sam plik bazy i
dziennika, nie mapowanie SHM. To nie regresja 0.2.23/0.2.24, a inna przyczyna o
identycznym kodzie błędu. Wyłączanie ochrony ani zmiana ACL nie są rozwiązaniem.

## Poprawka

- `NativeStorage.verifyRootWritable` sprawdza zapis w folderze **przed**
  otwarciem SQLite — wywoływane w `openStartupNotebook`, tuż przed utworzeniem
  połączenia (plik `silique-io-probe.tmp`, usuwany w `finally`). Zablokowany
  folder daje `StorageRootWriteBlocked`, a nie 778 z SQLite — komunikat mówi o
  folderze, podaje błąd systemu i nie twierdzi, że baza jest uszkodzona.
  Sprawdzenie dotyczy folderów z istniejącą bazą: pierwszy start jest już
  weryfikowany przez `prepareChosenRoot`, a dodatkowy zapis przy każdym otwarciu
  magazynu tylko opóźniał start (wykryte testem `hidden_folder_autolock`).
- Komunikat zawiera dotychczasowe, sprawdzone wskazówki Windows („Historia
  ochrony”, „Kontrolowany dostęp do folderów”, „Zezwalaj aplikacji…”, „Nie
  wyłączaj ochrony”), a treść jest wspólna z `prepareChosenRoot`, więc żadna
  ścieżka nie wymyśla własnej przyczyny.
- Nowa akcja **„Przenieś notatki”**: kopiuje `silique.sqlite` razem z `-wal` i
  `-journal` (bez `-shm`, który SQLite odbudowuje z dziennika) oraz `markdown/`
  bez podążania za dowiązaniami, do katalogu tymczasowego w wybranym folderze,
  otwiera kopię, sprawdza `quick_check` i liczbę dokumentów, dopiero potem
  zmienia nazwę na `Silique Vaults` i zapisuje nową lokalizację. Oryginał nie
  jest zapisywany, przenoszony ani usuwany.
- Kopiowanie bajtowe jest dopuszczalne **tylko** dlatego, że ta sama blokada
  zatrzymuje każdego pisarza: w zablokowanym folderze nie ma współbieżnego
  zapisu. To nie jest ogólny fallback zastępujący backup SQLite — ścieżka
  odzyskiwania (`NativeStorageRecovery`) pozostaje bez zmian i nadal odmawia
  (`SQLITE_IOERR_LOCK`), gdy źródła nie da się otworzyć.

## Ograniczenia

- Nie wykrywamy marki filtra: Kontrolowany dostęp, antywirus, udział tylko do
  odczytu wyglądają z Darta identycznie. Komunikat podaje fakt i błąd systemu.
- Brak porównania skrótów Markdown po kopiowaniu; sprawdzana jest baza.
- Kopia nie jest snapshotem transakcyjnym. Jeśli inny, dozwolony proces pisze do
  zablokowanego folderu w trakcie kopiowania, wynik może być niespójny —
  `quick_check` to wykryje i wtedy lokalizacja nie zostanie zmieniona.
- Aplikacja nie zmienia ustawień ochrony Windows i nie wymaga uprawnień
  administratora.
