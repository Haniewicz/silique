# Silique 0.2.23+32 — opublikowane

[Publiczne wydanie](https://github.com/Haniewicz/silique-releases/releases/tag/v0.2.23)
(opublikowane 2026-10-25T19:37:03Z, nie szkic, nie prerelease, osiem zasobów:
siedem instalatorów i `SHA256SUMS.txt`).

Zgłoszenie właściciela (Windows): aplikacja zadziałała po pierwszym uruchomieniu,
a przy każdym kolejnym włączeniu pokazuje ekran „Nie udało się otworzyć Silique”
z `SqliteException(778): while executing, disk I/O error` i instrukcją o pęku
kluczy. Objaw dotyczy polecenia `PRAGMA journal_mode=WAL` wykonywanego na
**istniejącej** bazie: nowy plik bazy da się otworzyć, ponowne otwarcie już nie.
Przyczyny na komputerze właściciela **nie potwierdzono** — brak dostępu do tego
Windows. Nie zmieniano ustawień ochrony systemu i nie deklaruje się, że
przywrócono zapis do konkretnego folderu.

## Zmiana

1. **WAL nie jest już warunkiem startu.** Przełączenie na WAL jest ponawiane
   (3 próby), a gdy folder nadal odmawia plików `-wal`/`-shm`, baza pracuje dalej
   na dzienniku wycofywania (`journal_mode=delete`) z `synchronous=FULL`.
   Silique zapisuje z jednego połączenia, więc trwałość danych jest taka sama;
   kolejne uruchomienie ponownie próbuje WAL i wraca do niego, gdy folder zacznie
   go akceptować. W trybie zapasowym nie zmienia się zawartość notatek.
2. **Ponawianie zamiast jednej próby.** Otwarcie pliku bazy i przełączenie
   dziennika są ponawiane po 300 ms; antywirus, klient synchronizacji czy
   instalator trzymający uchwyt przez chwilę nie kończą już startu.
3. **Zapis sprawdzany przed oddaniem notebooka do UI.** `BEGIN IMMEDIATE` +
   zapis + `ROLLBACK` dowodzi, że baza przyjmuje zmiany; baza tylko do odczytu
   kończy start czytelnym błędem zamiast pokazywać puste notatki.
4. **Czytelny komunikat zamiast tekstu o kluczach.** `StorageOpenFailure` podaje
   prawdziwą ścieżkę pliku, komunikat SQLite, obecność `-wal`/`-shm`, wersję
   SQLite i — wyłącznie jako podpowiedź, nigdy diagnozę — rozpoznany folder
   chmurowy. Ekran błędu startu ma teraz „Spróbuj ponownie”, „Wskaż inny folder”
   (notatki zostają na dysku) i „Kopiuj diagnostykę”.
5. **Log diagnostyczny poza folderem notatek** — `silique-diagnostics.log` w
   katalogu aplikacji, przycinany do 64 kB; nie koliduje z kontrolą obcych plików
   w folderze vaultów.
6. **Checkpoint przy zamykaniu okna** i po migracjach schematu, żeby następny
   start nie odtwarzał stron po nagłym zakończeniu procesu.
7. **Uchwyt bazy zwalniany przy każdym nieudanym starcie.** Ten błąd znalazł
   runner Windows: niedomknięte połączenie blokowało plik, więc folder zostawał
   zajęty dla ponowienia, aktualizatora i kopii użytkownika.

## Czego zmiana nie robi

- Nie usuwa ani nie nadpisuje `-wal`/`-shm` ani bazy: przy błędzie plik zostaje
  bajtowo nietknięty (jest na to test).
- Nie obchodzi Controlled Folder Access i nie zmienia ustawień systemu.
- Nie jest potwierdzoną diagnozą przyczyny na komputerze właściciela; usuwa
  ślepą uliczkę (start działa albo błąd mówi prawdę) i zostawia dowód w logu.
- Gdy folder blokuje także dziennik wycofywania, start nadal kończy się błędem —
  z prawdziwą przyczyną, ścieżką i logiem do przesłania.
