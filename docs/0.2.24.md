# Silique 0.2.24+33 — draft, nie publikować bez osobnej zgody

Zakres: Windows, ponowny start kończący się `SQLITE_IOERR_WRITE` (778), zarówno
na `PRAGMA journal_mode=wal`, jak i próbie przejścia na DELETE. Kod źródłowy
kandydata: `d519f47148d50b343d4f537633cb8f7e7fad351a`.

## Mechanizm i granice diagnozy

778 oznacza błąd zapisu VFS, nie potwierdzoną odmowę dostępu przez Defendera,
chmurę ani błąd separatorów ścieżki. SQLite 3.54.0 przy odtwarzaniu istniejącego
WAL może próbować skrócić plik SHM. Jeśli jest on mapowany, uruchamia
`winZeroSharedMemory` — ośmiobajtowy zapis nagłówka. Blokada tych bajtów powoduje
778. DELETE także otwiera/odzyskuje ten WAL, więc fallback 0.2.23 nie omijał
problemu. Przyczyny na komputerze właściciela nadal nie potwierdzono.

Na rzeczywistym runnerze Windows odtworzono ten mechanizm przez mapowanie SHM
oraz współdzieloną blokadę `LockFileEx` bajtów 0–7: oba stare PRAGMA zwracają 778.
Poprawiony `NativeStorage` pod tą samą aktywną blokadą uruchamia się, odczytuje
wartość zatwierdzoną wyłącznie w WAL, zapisuje kolejną, ponownie otwiera bazę,
a blokowany SHM pozostaje bajtowo niezmieniony. To test natywnego mechanizmu,
nie dowód, który proces lub filtr blokuje komputer zgłaszającego.

## Poprawka

- Windows wybiera `locking_mode=EXCLUSIVE` przed pierwszym odczytem schematu/
  dziennika; indeks WAL znajduje się w pamięci procesu. Rzeczywista blokada bazy
  nadal obowiązuje — druga instancja nie może swobodnie zapisywać do tej samej
  lokalizacji. Inne platformy zachowują dotychczasową politykę dostępu.
- Istniejący tryb dziennika jest zachowany. Nie ma już zmiany WAL→DELETE po
  błędzie I/O. Diagnostyka nie opisuje próby DELETE jako faktycznego trybu bazy.
- Wszystkie ścieżki nieudanego startu zamykają połączenie; diagnostyka zawiera
  kod podstawowy i rozszerzony. GetLastError jest tylko wskazówką, ponieważ
  dostarczona biblioteka nie eksportuje sqlite3_system_errno/file_control.
- Jawne odzyskiwanie tworzy nową, sprawdzoną przez quick_check kopię przez
  SQLite backup, z uwzględnieniem WAL i wszystkich nieinterpretowanych tabel,
  ciphertextów, identyfikatorów, intencji/tombstone'ów i kolejki synchronizacji.
  Markdown jest kopiowany bez przechodzenia przez dowiązania; nie jest częścią
  tej samej transakcji co SQLite. Oryginalne klucze nie są odtwarzane ani wymieniane.
- Odzyskana kopia **nie jest automatycznie aktywowana**. To snapshot z chwili
  odczytu; późniejsze zapisy do źródła nie znajdują się w niej. Otwarcie jest
  osobnym, świadomym wyborem istniejącego folderu, po zamknięciu innych kopii.
- Inicjalizacja notatek poprzedza zmianę wskaźnika. Oczekiwana wartość wskaźnika
  jest zapamiętana przed await; zapis jest serializowany przez FileLock i
  porównanie przed rename. Spóźniona udana inicjalizacja nie nadpisuje nowszego
  wyboru. Blokada dotyczy współpracujących pisarzy i nie wykrywa historii A→B→A.

## Zabezpieczenia i ograniczenia

- Nie kasujemy WAL/SHM, nie kopiujemy samej bazy jako naprawy i nie zmieniamy ACL.
  Read-only SQLite może jednak aktualizować księgowość SHM — nie deklarujemy
  niezmienności całego trójpliku przy ogólnym odzyskiwaniu.
- Sam BEGIN + zapis + ROLLBACK nie dowodzi trwałego zapisu na dysk. Regresje
  zapisują COMMIT i odczytują dane po ponownym otwarciu.
- Wyłączny odczyt recovery jest odrzucany kodem 3850 na Windows i POSIX;
  nie przedstawiamy go jako udanego obejścia. Przy nieczytelnym źródle recovery
  kończy się bezpieczną odmową. Główna poprawka startu korzysta z połączenia
  odczyt/zapis i została sprawdzona natywnie.
- Rzeczywista odmowa zapisu głównego pliku może pozostawić gorący dziennik
  wycofywania; readonly backup prawidłowo odmawia z kodem 776. Nie wolno go
  ignorować. Po zwolnieniu blokady SQLite musi sam zakończyć odzyskiwanie.
- Backup ogranicza powtarzanie blokad; nie obiecuje twardego limitu czasu
  zablokowanego natywnego wywołania systemu plików.
