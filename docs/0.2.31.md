## Przyczyna i poprawka

Zgłoszenie: `errSecParam` (**-50**) przy starcie na macOS.

Sonda natywna (`test/native/macos_keychain_probe.swift`, uruchamiana przez
`test/macos_keychain_test.dart` na runnerze macOS) rozstrzygnęła hipotezy pomiarem:

| Wariant | Wynik |
| --- | --- |
| odczyt pojedynczego klucza (z/bez `accessibility`) | `0`, wartość poprawna |
| zapis, aktualizacja, kasowanie | `0` |
| plugin `readAll` (accessibility jawna) | **-50** |
| plugin `readAll` (accessibility `nil`) | **-50** |
| plugin `readAll` na data-protection keychain | `0`, 0 wpisów (stare klucze są w keychainie plikowym) |

Wniosek: keychain plikowy odrzuca `kSecMatchLimitAll` razem z `kSecReturnData`
i `kSecReturnAttributes`. Hipotezy o `accessibility` oraz o złym łańcuchu
data-protection zostały **odrzucone**, nie „naprawione po omacku”. Klucze nie były
uszkodzone i nie zostały regenerowane.

Poprawka:

- `macos/Runner/MainFlutterWindow.swift`: metoda `listKeys` w istniejącym kanale
  `silique.notes/keys` — `kSecReturnAttributes` + `kSecMatchLimitAll` +
  `kSecUseDataProtectionKeychain: false`, **bez** `kSecReturnData`; przy
  `errSecItemNotFound` zwraca pustą listę, inne błędy jako `keychain_list_failed`.
- `lib/storage/secure_keys.dart`: `_SystemKeys.readAll()` na macOS listuje klucze
  natywnie i czyta każdy przez `_storage.read(key:)`; pozostałe platformy bez zmian.
- Sonda sprawdza ścieżkę wydania (atrybuty + odczyt pojedynczego klucza), a status
  pluginowego `readAll` pozostaje diagnostyką.
